# 1. Product Overview

Reverse API Engineer is a professional web-based application that enables users to discover, inspect, understand, reverse-engineer and generate usable API clients from the actual network communication performed by websites.

The application uses the existing Reverse API Engineer CLI as its underlying engineering engine.

Instead of requiring users to install packages, open terminals, enter CLI commands, configure execution environments or manually inspect browser developer tools, the product provides a centralized graphical interface.

Users interact exclusively with the frontend.

The backend receives user requests, validates them, executes supported CLI operations in a controlled server-side environment, processes execution results and returns structured information to the frontend.

**The terminal and backend execution environment must never be exposed to ordinary users.**

The frontend must not display a terminal emulator, shell prompt, raw command input, backend filesystem, environment variables or unrestricted server execution controls.

Users should experience the application as a standalone API engineering platform rather than a graphical wrapper around a terminal.

## 1.1 Core Product Concept

The product transforms this:

- Opening a terminal.
- Installing Python and CLI dependencies.
- Configuring an AI provider.
- Running reverse-engineering commands.
- Opening browser sessions.
- Capturing network traffic.
- Inspecting HAR files.
- Generating API client code.
- Finding generated files.
- Running and debugging generated clients.

Into a guided web workflow:

1. Create a project.
2. Enter an authorized target website URL.
3. Describe the information or functionality to investigate.
4. Select an execution mode.
5. Start an API discovery session.
6. Monitor progress through the dashboard.
7. Inspect discovered requests and endpoints.
8. Review the generated API client.
9. Test the generated client.
10. Download or export the completed project.

## 1.2 Product Objectives

1. Provide a professional frontend for the original Reverse API Engineer engine.
2. Hide all backend terminal and CLI operations from end users.
3. Support controlled execution of CLI commands through a backend service.
4. Provide agent-based and manual API discovery workflows where technically supported.
5. Capture and analyze actual website network requests.
6. Identify API endpoints, methods, headers, parameters and request payloads.
7. Generate typed API clients in supported programming languages.
8. Support API client regeneration from previously captured traffic.
9. Allow users to review, organize and manage multiple projects and runs.
10. Provide structured execution logs and error reporting without exposing server internals.
11. Support configurable AI providers and models through protected backend configuration.
12. Provide secure browser sessions and authentication handling.
13. Allow generated code and artifacts to be inspected, tested and downloaded.
14. Maintain a professional developer-focused user experience.
15. Build an architecture that can eventually support multiple users and isolated execution environments.

## 1.3 Product Scope

### Included in the initial product

The reference repository is:

https://github.com/kalil0321/reverse-api-engineer

The application must use the original project's actual capabilities as its functional foundation rather than inventing a replacement engine.

## 2.1 Existing Engine Capabilities

The reference engine supports:

1. Browser-driven website exploration.
2. AI-agent-driven browsing.
3. Network traffic capture.
4. HAR-based API inspection.
5. API client generation.
6. Multiple AI coding backends.
7. Multiple programming language outputs.
8. Saved execution history.
9. Previous run inspection.
10. Re-engineering saved captures.
11. Generated client execution.
12. JSON-based non-interactive CLI execution.
13. Structured run information and status reporting.

## 2.2 Existing Execution Modes

### Agent Mode

The AI agent visits a target website, performs the requested task, interacts with the website and captures relevant network activity.

The generated client is based on observed network communication.

### Manual Mode

The user manually interacts with a browser while the engine captures network traffic.

The application must provide a suitable browser-session experience before claiming full browser control through the web interface.

### Engineer Mode

The engine reuses a previously saved capture and generates or regenerates an API client without repeating the original browsing process.

### Supported Browser Providers

The reference engine includes browser integration options such as:

- Chrome MCP.
- Playwright MCP / automatic browser mode.
- Vercel agent-browser.

Provider compatibility must be checked against the installed CLI version.

### Important Integration Constraint

The original engine's manual browser mode and Chrome MCP mode have environment-specific requirements.

A browser running on the backend server is not automatically the same as a user's local Chrome browser.

Therefore:

- MVP should prioritize supported headless Playwright-based agent execution.
- Manual capture should use an explicitly supported remote-browser or local-browser bridge architecture.
- Chrome MCP must not be advertised as available in hosted mode unless its connection and session requirements are genuinely satisfied.
- HAR upload/import can serve as an alternative capture workflow.
- Provider availability must be determined from actual backend configuration and health checks.

## 2.3 CLI Integration Contract

The backend should communicate with the installed CLI through its documented non-interactive interface wherever possible.

Relevant command categories include:

- Agent execution with JSON output.
- Listing previous runs.
- Showing run details.
- Engineering an existing run.
- Running generated clients.
- Reading structured status and results.

The CLI should be invoked as a controlled subprocess, not as an unrestricted shell interface.

The backend must use argument arrays, validated inputs, explicit working directories, process timeouts and controlled environment variables.

The integration must be compatible with the installed and pinned CLI release.

The backend must not assume that an interactive terminal screen can be safely parsed as a structured API response.

# 3. System Architecture

## 3.1 High-Level Architecture

The system consists of five primary layers.

### Layer 1 — Frontend

Next.js application responsible for all user-facing interactions.

Responsibilities:

- Dashboard.
- Projects and workspaces.
- New discovery workflow.
- Execution monitoring.
- Endpoint inspection.
- Code viewer.
- Generated client management.
- AI provider settings.
- User preferences.
- Notifications and error states.

### Layer 2 — Backend API

FastAPI application responsible for authentication, authorization, request validation, orchestration and communication between frontend and execution workers.

Responsibilities:

- REST API endpoints.
- WebSocket connections.
- Job creation.
- Job status management.
- CLI process orchestration.
- Project and run metadata.
- Artifact access.
- AI provider configuration.
- Usage tracking.
- Audit events.

### Layer 3 — Background Execution Worker

A separate backend worker executes long-running CLI processes.

Responsibilities:

- Accept validated jobs.
- Prepare isolated working directories.
- Invoke the CLI.
- Collect stdout and stderr.
- Parse structured JSON responses.
- Track progress.
- Manage timeouts.
- Handle cancellation.
- Persist artifacts and run metadata.
- Notify the frontend.

The worker must not execute arbitrary commands supplied by a user.

### Layer 4 — Reverse API Engineer Engine

The original CLI is the underlying engineering engine.

It is responsible for its supported browser, agent, capture, analysis, client-generation and client-execution capabilities.

The web application should integrate with it rather than unnecessarily reimplementing its core functionality.

### Layer 5 — Database and Artifact Storage

Persistent storage for users, projects, execution history, settings, metadata and generated artifacts.

Use PostgreSQL for production and a private filesystem or object storage for artifacts.

## 3.2 Architecture Flow

```text
                 USER
                   |
                   v
          NEXT.JS FRONTEND
                   |
                   | REST API / WebSocket
                   v
             FASTAPI BACKEND
                   |
          Authentication & Validation
                   |
                   v
             JOB QUEUE
                   |
                   v
          BACKGROUND WORKER
                   |
                   v
       PRIVATE CLI SUBPROCESS
                   |
                   v
       REVERSE API ENGINEER
                   |
          +--------+--------+
          |                 |
          v                 v
      BROWSER           AI ENGINE
      CAPTURE            ANALYSIS
          |                 |
          +--------+--------+
                   |
                   v
            GENERATED CLIENT
                   |
                   v
          ARTIFACT STORAGE
                   |
                   v
          FASTAPI BACKEND
                   |
             REST / WS
                   |
                   v
           NEXT.JS FRONTEND
                   |
                   v
                  USER
```

## 3.3 Critical Architecture Rules

1. Frontend must never invoke the CLI directly.
2. Frontend must never access the backend filesystem.
3. Frontend must never receive unrestricted server command execution capability.
4. CLI execution must happen only on the backend worker.
5. Long-running processes must not block ordinary HTTP requests.
6. Every execution must have a unique run ID.
7. Every execution must be associated with an authorized project and user.
8. WebSocket connections must authenticate and enforce project access.
9. Generated files must be served through authorized download endpoints.
10. Backend secrets must never be exposed to the browser.
11. Execution must be isolated from other users' projects.
12. All job inputs must be validated before execution.
13. All process outputs must be parsed and sanitized before display.
14. User cancellation must stop the corresponding process and child processes safely.
15. Failed processes must leave a consistent, recoverable job state.

## 3.4 Recommended Deployment Architecture

### Initial Deployment — Local / Self-hosted

- Next.js frontend.
- FastAPI backend.
- Local background worker.
- Installed Reverse API Engineer CLI.
- Local browser runtime.
- SQLite or PostgreSQL.
- Private artifact directory.

The application can initially run on the developer's own machine while the CLI executes in the background.

### Future Deployment — Hosted SaaS

- Frontend hosting.
- Backend API hosting.
- Dedicated worker containers.
- Job queue.
- PostgreSQL.
- Private object storage.
- Isolated browser execution environments.
- Per-user resource and usage limits.

Hosted SaaS must not share unrestricted execution environments between users.

# 9. API Discovery — Primary Workflow

This is the most important functional section of the product.

The interface must provide a guided workflow that allows a user to initiate a discovery session without using terminal commands.

## 9.1 New Discovery Form

### Required Fields

- Target website URL.
- Task or discovery objective.

Example:

Target URL:

`https://example.com/jobs`

Task:

`Find the API used to search and retrieve job listings, including pagination and filters.`

### Optional Fields

- Project.
- Execution mode.
- Output programming language.
- AI provider/model.
- Browser provider.
- Additional authorized navigation instructions.
- Headless/headed option, where supported.
- Execution timeout within administrator limits.

## 9.2 URL Validation

Validate:

- URL syntax.
- HTTP/HTTPS protocol.
- Domain and host.
- Blocked private/internal destinations.
- Unsupported URL schemes.
- Unsafe redirect destinations.

All target browsing must follow the deployment's authorized-use policy.

## 9.3 Task Input

The user must be able to describe the desired functionality in natural language.

Examples:

- Discover the search API on a careers page.
- Identify pagination requests.
- Find product listing endpoints.
- Understand how filters are submitted.
- Identify the request used to retrieve profile information on an authorized test account.
- Generate a TypeScript client for an observed public endpoint.

The application should provide example prompts and clear input guidance.

## 9.4 Execution Mode Selection

### Agent Mode

The AI agent controls the supported browser provider and performs the requested task.

### Manual Mode

The user interacts with a supported browser session while traffic is captured.

This mode must only be enabled when the necessary browser connection is operational.

### Engineer Mode

The user selects a previous compatible capture and regenerates the API client.

The UI must prevent selection of captures that cannot be used by the selected engine version or provider.

## 9.5 Output Language Selection

Support the languages exposed by the installed engine:

- Python.
- JavaScript.
- TypeScript.
- Go.
- Java.
- C#.
- PHP.
- Ruby.
- C.
- PowerShell.

The available list must be synchronized with the engine's actual supported capabilities.

## 9.6 Execution Confirmation

Before starting, show:

- Target URL.
- Task description.
- Execution mode.
- Browser provider.
- Selected AI configuration.
- Output language.
- Estimated resource constraints, if known.
- Important authorization notice.

The user confirms by selecting Start Discovery.

## 9.7 Job Creation

After confirmation:

1. Backend validates the request.
2. Backend checks project access.
3. Backend checks provider availability.
4. Backend creates a unique run record.
5. Backend creates an isolated execution directory.
6. Backend enqueues the job.
7. Worker invokes the appropriate supported CLI operation.
8. Frontend receives the run ID.
9. Frontend opens the execution monitoring view.

The frontend must not wait synchronously for the entire execution to finish.

## 17.4 Credential Protection

- Never expose credentials in frontend responses.
- Store credentials using secure secret storage or encryption at rest.
- Mask credentials.
- Never log keys or tokens.
- Exclude secrets from exports.
- Limit access to the execution worker.
- Support credential replacement and revocation.

## 17.5 Provider Authentication Architecture

Some reference CLI providers reuse local CLI authentication or user-specific authentication environments.

The backend must explicitly manage the required authentication method.

It must not assume that an API key is mandatory for every provider or that a user signing into a browser automatically authenticates a backend CLI provider.

For hosted multi-user deployment, provider credentials and identity isolation require dedicated design.

# 23. Security Architecture

Security is a core product requirement because the application interacts with external websites, browser sessions, generated code, provider credentials and backend processes.

## 23.1 Backend Security

- Authentication and authorization.
- Input validation.
- CSRF protection where applicable.
- Secure session management.
- Rate limiting.
- Strict CORS.
- Secure HTTP headers.
- Safe error handling.
- Database query parameterization.
- Dependency security updates.
- Audit logging.

## 23.2 CLI Execution Security

- No unrestricted shell endpoint.
- Fixed executable path.
- Validated command arguments.
- No string-concatenated shell commands.
- Restricted environment variables.
- Per-job working directories.
- Process timeouts.
- Process-tree termination.
- Resource limits.
- Worker isolation.
- Controlled stdout/stderr processing.
- No cross-project filesystem access.

## 23.3 SSRF and Browser Security

Because users provide target URLs, the application must defend against server-side request forgery.

Requirements:

- Allow only supported HTTP/HTTPS schemes.
- Block loopback and private network targets by default.
- Block cloud metadata addresses.
- Resolve and validate DNS destinations.
- Revalidate redirects.
- Prevent DNS rebinding where feasible.
- Restrict access to internal infrastructure.
- Isolate browser sessions.
- Prevent unauthorized access to internal services.
- Apply destination policies to browser navigation and generated client execution.

Authorized private testing environments may be supported through an explicit administrator-controlled allowlist.

## 23.4 Browser Session Security

- Isolate cookies and sessions.
- Do not reuse sessions across unrelated users.
- Protect session artifacts.
- Avoid exposing browser debugging ports.
- Do not expose raw browser control endpoints publicly.
- Clean up sessions after expiry.
- Require explicit user authorization for authenticated browsing.

## 23.5 AI Security

- Treat website content as untrusted input.
- Defend against prompt injection.
- Do not expose provider credentials to the model.
- Limit tool access.
- Validate model-generated outputs.
- Restrict filesystem access.
- Prevent unauthorized generated-code execution.
- Maintain audit trails.

## 23.6 Authorized Use

The application must be designed for websites and accounts the user owns or is authorized to test.

It must not provide features intended to bypass access controls, extract credentials, evade security controls or exploit unauthorized private endpoints.

# 32. Final Product Definition

Reverse API Engineer is a web-based API engineering platform powered by the original Reverse API Engineer CLI.

The frontend provides a complete graphical experience for project management, website discovery, API inspection, request/response analysis, capture management, client generation, client execution and run history.

The backend privately orchestrates the CLI, browser automation, AI providers and artifact storage.

Users interact with the application exclusively through the frontend. They never need to access the backend terminal or manage CLI commands manually.

The original engine remains the source of core reverse-engineering capabilities. The web application adds a secure, structured, responsive and user-friendly interface around those capabilities.

**Primary development priorities:**

1. Correct integration with the original CLI.
2. Complete separation of frontend and backend execution.
3. Secure hidden terminal architecture.
4. Reliable background job processing.
5. Accurate API capture and endpoint inspection.
6. Functional API client generation.
7. Safe artifact and generated-code handling.
8. Real-time execution monitoring.
9. Professional developer-focused UI/UX.
10. Maintainable and extensible architecture.

**The final goal is not a terminal displayed inside a browser. It is a complete web application whose backend privately operates the engineering engine.**
